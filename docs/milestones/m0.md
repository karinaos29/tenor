## What was measured
- Health round trip in the browser: 1–27 ms on localhost (shown on the card).
- Server-side ping handling: 0.05–0.09 ms per ping (`backend/logs/latency.jsonl`, stage `health.server`).
- Tests: backend 8 passed; frontend 10 passed; `npm run typecheck` clean; `npm run build` OK.
- UI checked at 1280 px (light) and 900 px (dark), in the connecting, connected and offline states, plus automatic recovery after restarting the backend.

## Open questions
1. **`docs/architecture.md` is missing.** `CLAUDE.md` and the kickoff prompt call it the source of truth, but it isn't in the repo or anywhere in Downloads/Desktop/Documents. M0 was built from `CLAUDE.md` and the skills alone. **M1 needs it** for the event list and the audio-gateway contract.
2. **Speaker labels (judgment call):** diarization gives "speaker 0/1", not "caller/you". Options: (a) the user says a short line at the start ("I'm using Tenor on this call"), and that voice becomes "You"; (b) a one-tap "Swap speakers" control. I recommend (a), with (b) as a fallback.
3. **Replay WAVs:** should the two scripted calls be recorded by a person, or generated with two TTS voices (for example `gemini-3.8-flash-tts`)? TTS can be reproduced and scripted exactly. A human recording sounds more realistic through a speaker.

## Risks for M1 (Hear)
- **Browser audio processing:** `getUserMedia` defaults (`noiseSuppression`, `autoGainControl`) may treat the phone speaker's voice as noise and damp it. Mitigation: request the constraints explicitly, A/B them on a real speakerphone call, and show a mic level meter on the Start screen.
- **Audio format:** MediaRecorder's webm/opus is easy but adds chunking delay, and replay files would take a different path. Recommendation: an AudioWorklet producing 16 kHz linear16 PCM in ~100 ms frames, which is exactly what the file replay source will also emit. Then live and replay share one pipeline, as required.
- **Deepgram streaming:** the socket closes after silence unless KeepAlive messages are sent. Interim results change until `is_final`. The key must stay server-side, so the browser streams to our gateway and never to Deepgram. Each of these needs a timeout and a visible fallback ("Transcription paused, reconnecting").
- **Diarization on one mic:** a phone speaker plus a near voice in one room, short back-and-forth turns, and labels on interim results that may flip. Mitigation: show labels only on final segments; enrollment as in question 2; measure speaker-label accuracy on the replay calls.
- **Latency budget:** the M3 target is "flag within 2 s". Deepgram finals plus extraction need to fit in roughly 1 s. M1 will log `stt.interim` and `stt.final` latencies from the first frame onward.

## Known issues
- The latency log grows by one line per ping (every 5 s while a tab is open). That's fine for now; M4 may sample or rotate it.
- The browser console logs failed WebSocket attempts while the backend is down. That's native browser behavior and can't be silenced. The UI shows the offline state.

## Demo script (M0)
1. Start the backend (`uv run uvicorn app.main:app --reload`) and the frontend (`npm run dev`), then open http://localhost:5173. The card shows "Connected", the response time, and which keys are set.
2. Stop the backend. The card switches to "Can't reach Tenor's server. Trying again in N s."
3. Start it again. The card reconnects by itself, with no reload.
